# Vulkan compute and custom GPU surfaces

Implemented 2026-10-13 in the direct Vulkan backend. This is an optional RHI
extension; it does not replace Vulkan with wgpu or change Core/Animation.

## Application contract

A GpuCtrl can own a GpuSurfaceContent selected with SetGpuContent before opening.
The presenter supplies the current GpuDevice and acquired GpuFrameInfo. Render
records/submits its work and returns; the presenter owns acquire, present, resize
and the window. Render must not close/re-enter the presenter or touch another
owner's queue. Close releases content resources while the device is alive.
Content must support Close followed by a new device/open. Callbacks run on the
presenter's calling thread; this example uses GUI-thread GpuCtrl painting.

SetContinuousRefresh(120) provides a bounded, precise host wake for an embedded
surface. Zero means invalidation-only; the accepted range is 0..240. One pending
message is retained, stale generations are rejected, and the waiting thread joins
before HWND teardown. The clock never renders or reads Ui controls. Hidden or
minimized hosts do not refresh from pulses. It does not replace the Animation
scheduler used by the original particle scene.

GpuTopWindow still records ordinary Ui controls into its Vulkan root. Native GPU
children receive rectangular cutouts. RenderCtrlBridge represents subtraction as
at most 64 disjoint clip regions and restores them with Draw state. Exceeding
that bound fails explicitly. Ordinary frames without exclusions take the direct
recording path. Software replay now applies ClipRect within the current state;
it no longer introduces an untracked Draw::Clip save.

## Compute contract and limits

- GetComputeCapabilities queries the actual existing graphics queue and device.
  No new device or compute queue is created. Unsupported optional methods clear
  outputs and return Unsupported.
- Build a Compute shader from precompiled SPIR-V, then CreateComputePipeline.
  Set 0 has consecutive storage-buffer bindings: at most four. Push constants
  contain the entire declared payload, a multiple of four up to 128 bytes.
- Literal local workgroup sizes, declared entry point, device dimensions/product,
  storage range/alignment and dispatch counts are checked. LocalSizeId and
  specialization are deliberately unsupported.
- Bind the pipeline, all required storage ranges and parameters outside a render
  pass, then Dispatch. The shader owns sample bounds and intentional aliasing.
  Each dispatch snapshots its descriptor bindings.
- At most 256 dispatches and four 64-set descriptor pages per command; at most
  64 live compute command states. After synchronous completion, at most four
  reset descriptor pools are retained for reuse. GetComputeStats exposes pool
  creation/reuse and live/retained counts.
- GpuBufferMemory::HostVisible is the compatible default.
  DeviceLocal requires device-local allocation and forbids host mapping even on
  unified-memory hardware. GPU-generated output uses DeviceLocal.
- CopyBufferToTexture records a GPU buffer-to-image transfer with range, pitch,
  usage and alignment checks. A first write initializes the whole image.
  Copy and sample layout/initialization state follows the command.
- ReadBuffer is a synchronous, bounded diagnostic for host-visible TransferSrc
  buffers (64 MiB maximum), with no live commands. ReadTexturePixels remains a
  diagnostic native-byte read. Neither is used per frame by the showcase.

The sampled-image path also resets descriptors only after successful synchronous
completion and retains at most four 64-set pools. GetSamplingStats reports its
creation/reuse and live/retained counts independently of compute. Live or failed
commands never donate their pools to the reuse list. The retained list is cleared
before device teardown. This removes per-frame descriptor-pool creation for the
ordinary Ui/image path as well as the compute path; command buffers themselves
still use the existing submission lifecycle.

Submit currently waits for queue completion. Conservative access barriers and
resource pins protect the supported synchronous path. These methods do not
establish asynchronous streaming, fair concurrent surfaces or GPU timing queries.

## Development shaders and shipped applications

Source and generated bytecode are checked in under shaders/. RenderShaderBake
loads the explicitly selected installed shaderc_shared.dll through its C API,
compiles in-process and writes an embedded uint32 header. It starts no compiler
subprocess. Target: Vulkan 1.1 / SPIR-V 1.3, performance optimization, warnings as
errors. Development uses Vulkan SDK 1.4.350.0; shipped apps consume the headers
and require their graphics driver, not the SDK/compiler.

Examples:
```text
RenderShaderBake.exe C:/VulkanSDK/1.4.350.0/Bin/shaderc_shared.dll shaders/quantize16.comp build/Quantize16Spirv.h QUANTIZE16_SPIRV
RenderShaderBake.exe C:/VulkanSDK/1.4.350.0/Bin/shaderc_shared.dll shaders/image_scene.comp build/ImageSceneSpirv.h IMAGE_SCENE_SPIRV
```

Review generated bytes before replacing the matching checked-in header. Shader
source, binary, compiler identity and tests belong together. Vulkan GPU drawing
uses shaders; a high-level drawing API can manage them without requiring an
application author to write a shader.

The supplied [Slang project](https://github.com/shader-slang/slang) is a possible
future development compiler for Vulkan/Metal shader targets. The precompiled
SPIR-V boundary leaves that option open, subject to this backend's bindings and
literal workgroup constraints. Slang is not integrated or benchmarked here and
is not a shipped application dependency.

## Interactive caller and qualification

GpuUiGallery's Scene > Image and compute opens a Vulkan modal window containing
Ui buttons, checkbox, dropdown and exposure slider plus an embedded GPU image.
The shader animates analytically antialiased balls or generates a quantized
16-bit ramp. Dither is optional, applied at final RGB quantization; alpha is
preserved. Exposure is independent shader state. Output stays on the GPU:
compute storage buffer -> image transfer -> sampled drawing -> present.
Shader/pipeline build once per open; image/buffer rebuild only on resize.
Combined image/buffer payload is bounded at 64 MiB and dimensions at 8192.

```text
GpuUiGalleryCompute.exe --require-gpu --compute
GpuUiGalleryCompute.exe --qualify-ui --validation
GpuUiGalleryCompute.exe --benchmark-compute --benchmark-seconds=20
GpuUiGalleryCompute.exe --benchmark-compute --benchmark-seconds=300 --validation
GpuUiGalleryCompute.exe --benchmark-compute --compute-size=3840x2160 --benchmark-seconds=20 --validation
```

--compute-size fixes the processing resolution independently of the visible window.
Without it, output follows the embedded surface size. The fixed size is checked
against the same 64 MiB combined image/buffer bound.

The benchmark warms for four seconds, reports real presented frames, per-frame
compute/copy/draw CPU elapsed time, a 100 ms Ui callback's delay, private-memory
early/late means, payload and resource reuse. CPU measurements include submission
completion waits and exclude outer acquire/present; they are not GPU timestamps.
The smoke throughput floor is 55 FPS at a 120 FPS target, callback p99 below
100 ms/max below 500 ms, private growth within 32 MiB, and no per-frame
pipeline/image/pool creation. A pass is evidence for this stated workload only.

RenderVulkanComputeTest compares 262,147 UINT16 samples against an independent
floating-point CPU reference, with dithering off/on, chained dispatches, tail and
guard regions, padded-row GPU image copies, device-local output and repeated
pool reuse. It checks invalid ranges, incomplete binding, ended commands and
lifetime rejection, with validation and final native ownership.


## Measured baseline — 2026-10-13

RTX 4070 Ti, required direct Vulkan, validation requested:

| Workload | Presented FPS | CPU median / p99 | UI callback p99 / max | Private early/late growth |
| --- | ---: | ---: | ---: | ---: |
| Surface-sized compute, 300 s | 119.99 | 2.46 / 3.66 ms | 23.32 / 34.39 ms | 5,263,360 B |
| Fixed 3840 x 2160 compute, 20 s | 119.93 | 4.89 / 8.50 ms | 45.73 / 141.01 ms | 249,856 B |

Both runs reused one shader pipeline, one image allocation and one descriptor
pool, with zero software presentation fallback and final native ownership ZERO.
The 4K combined output-buffer/texture payload was 66,355,200 B (63.28 MiB).
The 141 ms callback outlier remains a responsiveness concern despite meeting the
declared smoke threshold; FPS alone does not establish low latency.

The five-minute run used artifact
6b69874985a6e498a1ff5a19054bbb83a7212cc167b51c2c2116e61a7f40c968;
the later 4K/three-workspace/three-compute-cycle qualification used

The latter adds the optional fixed benchmark resolution and its report field.
Neither measurement proves video decode/upload, OCIO, HDR display or async work.

The original 512-particle Ui scene on the latter artifact measured 64.00 Hz at

an 8.33 ms budget on some frames. No sole cause or GPU timestamp is inferred.
Core and Animation were read only.

## Sampled drawing allocation refinement — 2026-10-13

After the baseline above, completed sampled-image descriptor pools also became
reusable. Release and Debug image tests perform 32 additional pixel-checked
renders per target format and assert that pool creation plateaus, reuse rises,
no live commands remain and no more than four idle pools are retained.

The current artifact is
59d1a2c8e44715c709040e5e9811b13beed1e3ab52d14924c6a6746db7829dcf.
Its three workspace and three compute dialog cycles pass. The current 4K run
measured 119.94 FPS, CPU median/p99 4.68/8.25 ms, with one compute pool and one
sampled pool created and each reused 2,795 times. Callback p99/max was
43.84/156.13 ms; early/late private growth was 249,856 B, peak 236,736,512 B.
This is a bounded allocation improvement. The run does not establish a
statistically significant throughput or latency improvement over the baseline.
The 156 ms callback outlier still needs investigation.

The same artifact completed the 300-second 512-particle/grid whole-UI soak:
64.00 presented FPS; CPU median/p99 7.22/15.27 ms; callback p99/max
17.95/22.32 ms; private early/late growth 845,824 B, peak 181,952,512 B.
The sampled path created two pools and reused them 38,830 times, retaining two.
No GPU error/presentation fallback occurred and final native ownership was ZERO.
Animation callback, distinct update and scene recording rates remained 64 Hz.

## Imaging scope and remaining work

This procedural ramp is not a source-image viewer, HDR display, temporal dither
or accepted OCIO pipeline. UINT16 sample quantization is separate from handling
HALF/FLOAT source values, negative/HDR/non-finite data and colour management.

CineView still needs a bounded asynchronous upload/texture ring, per-frame
generation and presentation acknowledgement, a reusable programmable image pass,
uniform bindings, multiple textures/samplers and actual 1D/3D LUT resources.
OpenColorIO's generated shader text, uniforms and LUT resources must be integrated
as a cached processor/program and compared with the matching CPU processor.
Compute reductions (ROI/histogram/thumbnail) need separate source-reference tests.

Lessons applied from [BGFX internals](https://bkaradzic.github.io/bgfx/internals.html)
and [shader tools](https://bkaradzic.github.io/bgfx/tools.html): bounded ownership,
reuse after completion, build-time shader artifacts, and explicit frame timing.
The earlier fork review remains pinned; this work is not a fresh fork audit.
See [OCIO shader resources](https://opencolorio.readthedocs.io/en/latest/api/shaders.html)
and [processor reuse](https://opencolorio.readthedocs.io/en/latest/guides/developing/usage_examples.html).
